# BESTCRM 标书中心 V1 第 6 步实施报告

- 日期：2026-09-05
- 状态：完成，等待用户确认
- 分支：`codex/bid-center-v1`
- 生产影响：无

## 完成范围

- 技术包、商务包和完整标书均新增提交、审批通过、驳回及正式版本冻结流程。
- 版本编号固定为技术包 `TS-Dn / TS-Vn`、商务包 `CP-Dn / CP-Vn`、完整标书 `QP-Dn / QP-Vn`。
- 技术包由机会指定的项目负责人提交、指定 Technical Manager 审批；商务包由机会指定的项目负责人提交、指定 Commercial Manager 审批；完整标书由项目负责人组装并提交、指定 Sales Manager 审批。
- 驳回不会覆盖或重新打开原稿；系统保存被驳回快照并创建下一份可编辑 `D` 版本，同时复制项目级变更理由和有效附件。
- 完整标书只绑定已批准的 `TS-V`、`CP-V` 和商业报价版本，冻结币种、总价、交期、付款条件、有效期和行项目。
- 完整标书获得批准后形成 `QP-V`，工作区同步进入 `approved`；第 7 步将基于该不可变版本生成输出文件。
- 版本比较覆盖变量、章节、标准条款、公共资料、商业字段、组件版本和附件 SHA-256。

## 完整性门禁

- 每次检查写入只增不改的结果、问题列表、操作者、时间及稳定的快照 SHA-256。
- 阻止缺少必填变量、缺少必填章节、未解决占位符、待澄清偏差、待复核修改理由缺失及必需附件缺失的提交。
- 商务包和完整标书同时校验已批准报价、总价、付款条件、有效期及有明细时的行项目合计。
- 提交操作会重新执行完整性检查；仅通过当前精确草稿来源的检查才能进入审批。
- 包提交后，数据库阻止移除其附件；正式版本及审批来源由数据库不可变约束保护。

## 权限和职责分离

- 提交人与审批人必须是不同用户；服务层和数据库层均执行该约束。
- Administrator 可检查流程和内容，但不能代替 Technical Manager、Commercial Manager 或 Sales Manager 审批。
- 所有提交、审批和驳回 POST 均重新检查机会责任人、角色、包状态和精确来源，不依赖界面按钮隐藏。
- 旧报价包路由不能修改或审批标书中心产生的 `QP`；只要机会已有标书工作区，也不能从旧入口新建报价包绕过完整性门禁。
- 工作区及包读取继续使用 SQL 层 `visibleToUserId` 机会范围。
- 待办和工作流事件发送给实际指定审批人或原提交人，并记录真实操作者和目标收件人。

## 数据库和审计

- 新增迁移 `039_bid_package_approvals.sql`，包括完整性检查记录、审批事件来源、驳回修订来源及职责分离约束。
- 技术包、商务包和完整标书的审查来源与客户发送修订来源分开记录，避免把内部驳回链误作客户修订链。
- 章节变更、附件、完整性检查和审批事件都绑定到精确的工作区及 `D/V` 来源。
- 被驳回稿、已批准正式版本、检查记录和事件历史保持可追溯，不原地覆盖。
