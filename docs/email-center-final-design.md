# BESTCRM 邮件中心最终方案

状态：方案冻结；发布候选 A 已通过本地验收，用户已于 2026-09-19 确认 Git 提交及新加坡部署。2026-09-20 已确认“邮件 -> 线索 -> 销售经理批准 -> 商机”及标准邮件完整性要求，详见 `docs/superpowers/specs/2026-09-20-bestcrm-lead-email-integrity-addendum.md`；发生冲突时以该补充规范为准。发布候选 B、C 仍按阶段实施。

## 1. 产品边界

1. 网易企业邮箱是完整邮件底稿和最终留存来源。
2. BESTCRM 是与询价、商机和项目协作有关的业务处理系统，不替代网易成为公司总邮件管理系统。
3. CRM 只接入公共业务邮箱 `sales@sunkaier.com` 的“收件箱”和“已发送”。
4. 个人邮箱不接入 CRM。员工在个人邮箱收到客户询价时，转发到 `sales@sunkaier.com`，或在 CRM 手工提交线索；新商机必须经销售经理批准后生成，后续统一通过 `sales@sunkaier.com` 沟通。
5. 网易黑名单负责将已确认的垃圾来源拦截到垃圾邮件文件夹；CRM 不读取网易的垃圾、广告、删除、草稿等文件夹。
6. `sales@sunkaier.com` 收件箱和已发送中的邮件全部先进入 CRM 待处理暂存，以避免漏掉客户询盘；进入暂存不等于永久归档。规则或 AI 只能提供分类建议，不能在导入前自动丢弃邮件。人工确认后，业务邮件进入长期档案，垃圾邮件和可删除的非业务邮件从 CRM 正文及文件库中清除。
7. 从 CRM 删除邮件只删除 CRM 副本，不删除或移动网易原邮件。

## 2. 邮件中心栏目

邮件中心固定为五个互斥栏目：

| 栏目 | 内容 | 处理结果 |
| --- | --- | --- |
| 待处理 | 尚未完成业务归类的新收件 | 人工转为线索、关联已有商机、标记垃圾或标记非业务 |
| 收件箱 | 已完成待处理并关联线索或商机的客户来信 | 线索批准后自动继承到商机；商机来信进入邮件时间线并通知负责人 |
| 已发件箱 | CRM 发出的、已关联商机的邮件 | 自动进入商机邮件时间线 |
| 垃圾邮件 | 人工确认或规则建议为垃圾的邮件 | 管理员可批量或单封从 CRM 永久删除 |
| 非业务邮件 | 系统通知、财务物流、正常订阅等非商机邮件 | 管理员可批量或单封从 CRM 永久删除 |

“待处理”不是普通收件箱的子集；一封邮件处理完成后必须离开待处理，进入收件箱、垃圾邮件或非业务邮件中的一个栏目，避免重复处理。

## 3. 新邮件归集规则

1. 新收件优先使用邮件 `Message-ID`、`In-Reply-To`、`References` 和主题中的 `[REF. 商机号码]` 自动识别商机。
2. 匹配成功：关联商机、进入收件箱和商机时间线，并通知该商机销售负责人。
3. 无法匹配：进入待处理，不得自动丢弃。
4. 获授权处理人在待处理中只能执行四种最终动作：
   - 转为线索并提交销售经理批准；
   - 关联已有商机；
   - 标记为垃圾邮件；
   - 标记为非业务邮件。
5. 最终动作必须采用数据库原子更新；多人同时处理时只有第一人成功，其他人看到“该邮件已由某人处理”。
6. CRM 使用邮箱、文件夹、IMAP UIDVALIDITY、UID、原始 Message-ID 和内容指纹去重。

## 4. 个人邮箱转发

1. 员工优先使用“作为附件转发（.eml）”发送到 `sales@sunkaier.com`，以保留原始发件人、时间、Message-ID 和附件。
2. 新询价可在主题前注明 `[新询盘]`；已有商机可注明 `[商机 800113]`，但这些只是人工提示，不直接绕过管理员确认。
3. CRM 识别公司内部转发人，并将原始客户作为客户邮件身份；转发员工记录为“询盘提供人”。
4. 多人转发同一原始邮件时，按原始 Message-ID 去重。
5. 转发邮件进入待处理，由获授权处理人转为线索或关联已有商机；线索经销售经理批准后生成商机，后续邮件统一使用 `sales@sunkaier.com`。

## 5. 客户可见的往来编号

1. CRM 内凡是回复客户邮件，发送前由服务器在主题末尾强制加入：`[REF. 商机号码]`。
2. 示例：`Re: Copper Sulfate Line – Technical Proposal [REF. 800113]`。
3. 对外只显示 `REF.`，不出现“商机”或 `Opportunity` 字样。
4. 已存在正确 REF 时不得重复添加；错误 REF 必须阻止发送并提示处理。
5. 未关联商机的邮件不能直接回复，必须先建立或关联商机。
6. 即使客户删除 REF，CRM 仍通过标准邮件会话头关联；下一次回复时重新补充正确 REF。
7. 网易中可通过 `REF. 800113` 搜索该商机相关往来。

## 6. 公共邮箱与实际发件人

1. SMTP 认证邮箱、From 地址和 Reply-To 地址统一为 `sales@sunkaier.com`。
2. 显示姓名、职务和邮件签名从实际对外发件人的 CRM 用户资料读取。
3. 示例：`David Chen | Lead Engineer <sales@sunkaier.com>`。
4. 已在网易 SMTP 实际验证动态显示名称能够保留。
5. 每封邮件记录撰写人、批准人、对外发件人、发送时间、商机和会话。
6. CRM 发送成功后，应把同一封原始邮件副本写入网易“已发送”，同时保留 CRM 归档，保证两端均可追溯。

## 7. 多人协作与发送审批

1. 每个商机只能有一名“客户沟通负责人”，默认为商机销售负责人。
2. 商务、主任工程师、协助工程师和售后人员加入商机项目组后，可以查看完整往来、添加内部备注并共同撰写草稿。
3. 项目组成员不能直接发送客户邮件；草稿必须提交给商机销售负责人。
4. 销售负责人可以同意发送、修改后发送或退回修改。
5. 对外发件人可以是实际撰写的技术/售后人员，也可以由销售负责人改为自己；批准人始终单独记录。
6. 同一客户来信只能存在一个有效回复草稿。开始编辑时显示当前编辑人；提交审核后草稿锁定；发送成功后其他旧草稿失效。
7. 管理员或销售经理只有在负责人请假、离职或明确代理时才能代批，必须保留代批审计记录。
8. 客户回复后通知商机销售负责人；必要时同时通知上一封邮件的实际对外发件人。

## 8. 唯一回复入口

1. 商机页页眉的“邮件”改名为“邮件往来”，只负责定位到往来沟通区域，不直接进入写信页面。
2. “往来沟通”栏目标题右侧保留唯一主按钮“回复客户”。
3. 删除每封邮件下方重复的“回复”，保留“查看原文/打开会话”。
4. 点击“回复客户”默认回复该商机最新客户来信；存在多个独立会话时先选择会话。
5. 桌面端和手机端调用同一回复流程；手机端可以把同一个按钮固定在底部，但不能形成第二套发送逻辑。

## 9. 阅读版面

1. 展开邮件时正文使用可用横向空间，不保留当前无意义的右侧大面积空白。
2. 纯文本邮件仅在展示时重排硬换行，不修改原始邮件；段落、列表、引用历史和签名结构必须保留。
3. HTML 邮件后续采用安全隔离方式显示原始格式，禁止脚本、表单和自动跳转；外部图片默认阻止，用户明确点击后才加载。
4. CID 内嵌图片、Logo、表格和附件应正确显示；附件集中放在正文下方。
5. 历史引用默认折叠，可展开查看。
6. 手机端取消正文左侧大缩进，长链接和宽表格不得撑破页面。

## 10. 保存格式

1. 每封进入待处理的收件和已发件都先以原始 MIME 邮件保存一份不可变 `.eml`，作为审核期间的完整底稿；页面展示优化不得修改该文件。确认属于业务的邮件转为长期不可变档案；确认并执行永久清理的垃圾邮件或非业务邮件，其 `.eml`、正文、邮件头和附件从 CRM 删除。
2. 数据库分别保存标准邮件头、纯文本正文、原始 HTML 正文、会话关联、分类状态和存储校验值，不能只保存浏览器处理后的文字。
3. HTML 正文展示前生成安全版本；原始 HTML 保持不变。纯文本正文可以在阅读时重排硬换行，但数据库中的原文保持不变。
4. 附件按原文件字节保存，并记录原文件名、MIME 类型、大小、SHA-256、Content-ID 和所属邮件；CID 图片从本地归档解析，不依赖外部临时链接。
5. `.eml`、附件和内嵌资源存放在非公开目录，浏览器只能经登录、权限检查和受控下载接口访问。
6. CRM 发件时只构造一次最终 MIME 原文；SMTP 发送、CRM 归档和写入网易“已发送”均使用同一份内容，避免两端正文、签名或附件不一致。
7. 保存成功的条件是原始 `.eml`、数据库索引和附件全部落盘并通过校验；其中任何一步失败都不得把邮件标记为完整归档。

## 11. 权限与删除

1. 系统管理员处理公共邮箱待处理邮件，并可查看全部公共邮箱邮件。
2. 商机销售负责人及获授权项目成员只查看其有权访问的商机邮件。
3. 个人邮箱不在 CRM 中展示或授权。
4. 垃圾邮件和非业务邮件只有管理员可以永久删除 CRM 副本。
5. 批量删除必须显示会话数、邮件数、附件数和空间，并要求明确确认；商机关联邮件、客户联系人关联邮件、已发送邮件及完整回复链不得进入可删除集合。
6. 删除操作只保留不含发件人、收件人、主题、正文、邮件头、文件名和附件的最小审计记录，并明确标注“网易原邮件保留”。
7. 新加坡生产环境中已经由管理员从 CRM 收件箱人工删除的历史记录不追溯、不恢复，也不要求为这些旧记录补做逐封审核；以新版本启用时间作为新规则起点。
8. 新版本启用后的永久删除必须同时保留不可变的“已清理身份标记”。该标记只保存邮箱连接、文件夹、UIDVALIDITY、UID，以及标准化 Message-ID 和内容指纹的不可逆摘要；不得保存发件人、收件人、主题、正文、完整邮件头、文件名或附件。导入服务命中该标记时只记录跳过结果，不重建正文、附件或邮件会话。该标记不是邮件归档，只用于防止 CRM 重导，也不操作网易原件。

## 12. 实施与发布决定

不采用一次性大改，分三个发布候选，每个候选均执行“本地实现 → 自动测试 → 桌面和手机截图确认 → Git 提交 → 新加坡备份发布 → 线上验证”。

### 发布候选 A：邮件栏目和阅读体验

- 五个互斥栏目及其查询语义；
- 非业务邮件分类、恢复与管理员批量/单封清理；
- 待处理的最终动作和处理结果；
- 全宽阅读、纯文本重排、手机适配；
- 收件原始 `.eml`、安全 HTML、纯文本和附件的完整保存及校验；
- 不改变 SMTP 发送和商机关联算法。

### 发布候选 B：归集与自动关联

- 生产 IMAP 来源收敛为 `sales@sunkaier.com/INBOX` 和 `sales@sunkaier.com/已发送`；
- 停止个人邮箱增量导入，但不删除已归档历史数据；
- 个人转发识别与待处理归集；
- `[REF. 商机号码]` 强制追加、自动匹配、去重和负责人通知；
- CRM 发件使用同一份 MIME 原文完成发送、CRM 归档并写入网易“已发送”。

### 后续候选 C：多人草稿与批准发送（本轮延后）

- 唯一回复入口；
- 一个有效草稿、编辑占用提示和版本冲突保护；
- 团队撰写、销售负责人审核、退回和批准发送；
- 撰写人、批准人、对外发件人和代批审计；
- 动态姓名、职务、签名和统一 `sales@sunkaier.com` 发件。

当前首批发布只处理“以后邮件的归集规则、阅读体验和保存格式”。多人草稿及发送审核不作为首批发布范围，也不阻挡发布候选 A、B 的本地验收。

## 13. 发布前硬门槛

1. 本地源代码必须与当前新加坡活动发布基线一致后再叠加改动。
2. 本地完整测试及邮件重点测试全部通过，无未解释失败。
3. 新加坡 `bestcrm.service`、PostgreSQL、Nginx 和实时收件服务必须健康；历史回填保持原有受控状态，不因部署自动启动。
4. 2026-09-19 已确认 `bestcrm-email-intake.service` 的失败源是仍被配置导入的个人邮箱 `markyang@sunkaier.com`。生产配置已保留备份并收敛为仅导入 `sales@sunkaier.com`；服务恢复为 `active/running`，随后一次增量轮询扫描并导入 3 封邮件、0 跳过。部署前后仍须再次核验服务和日志。
5. 不把历史人工删除邮件的逐封审核或身份恢复作为发布门槛；只确认新版本启用点、IMAP 当前游标和历史回填保持关闭，避免部署时主动重扫旧邮件。
6. 发布前创建并校验数据库、附件、原始 EML 和环境配置备份，确认磁盘空间及回退路径。
7. 涉及发送行为的验收邮件只发送到公司内部测试地址；不得向客户发送测试邮件。
8. 每个候选上线后验证健康接口、登录、五个栏目、自动归集、权限、桌面/手机布局和服务日志；验证失败立即回退。
