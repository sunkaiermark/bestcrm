# Phone layout

The shared application shell and all five standalone authentication pages load `mobile-layout.css`. Every CSS rule is inside `@media screen and (max-width: 860px)`; larger viewports keep the existing typography, tables and navigation. `mobile-layout.js` only adjusts presentation and restores table/diagram DOM positions when leaving the small-screen breakpoint.

On small screens the existing permission-filtered navigation is behind a menu button. Forms use one column with 16px text and larger controls. Simple list tables and independent work-package file rows become labelled cards; existing forms, action URLs, CSRF fields and event listeners are preserved. Detail tables use label/value pairs. Complex tables, original Office documents and diagrams retain local scrolling. Hidden upload controls keep their original hidden dimensions. Dialogs remain within the viewport. No endpoint, permission, migration or production configuration changes are included.

Validation uses an isolated PGlite database and rendered real application templates, with nonempty synthetic file-approval rows. Forty pages were checked at 320, 390 and 844 CSS pixels (120 checks). At 1366 pixels their visible element positions, dimensions, display and font sizes matched versions without the mobile hooks. Tests also cover unchanged form identity/CSRF/values, navigation keyboard behavior, dynamic tables, breakpoint restoration, independent rejection controls, public health and read-only Excel preview. Browser checks and screenshots are in `output/mobile-system-preview/`; test generation scripts are local preview tooling and not shipped as application routes.

Coverage includes workbench, opportunities, leads, customers, contacts, website inquiries, email inbox/compose, project execution list, analytics, users/roles/approval settings, technical templates/clauses, quotation package list, sales plans, development lists/new topic, account security and authentication. The shared rules apply to the remaining detail and edit templates as well, but each populated workflow and actual iOS/Android browser has not been individually verified. In particular real document-server rendering and large production charts need device acceptance after release. These changes are currently local and have not been deployed.
