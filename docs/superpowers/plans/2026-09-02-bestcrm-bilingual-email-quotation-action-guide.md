## 1. 实施目标

在不影响南京 CRM、不中断新加坡现有 CRM 的前提下，分阶段实现：

1. 登录后中英文切换和全部新增页面双语化。
2. 所有新商机先进入询价，由销售经理审核、查重、分配并转为商机。
3. 销售自行获得的线索可以快速提交，但不能绕过询价直接新建商机。
4. 每个商机设置一名项目主任工程师和多名协助工程师。
5. 建立受控的产品技术协议模板库，快速生成项目技术方案。
6. 技术方案、商务报价和完整报价包分别进行可追溯的版本管理。
7. 使用 `sales@sunkaier.com` 在 CRM 内收发业务邮件并归档。
8. 所有正式发送版本、邮件、附件、审批及操作记录可长期恢复。

详细业务规则以
`docs/superpowers/specs/2026-09-02-bestcrm-bilingual-email-center-design.md`
为准。本指南只规定实施顺序、验收标准和确认门。

## 2. 强制执行规则

### 2.1 一次只做一步

- 每次只实施下列一个步骤，不同时跨两个步骤修改。
- 当前步骤完成后，停止继续开发并提交验收报告。
- 只有用户明确回复“确认第 N 步”后，才能进入第 N+1 步。
- 用户提出调整时，只修正当前步骤并重新验收，不提前做后续功能。

### 2.2 本地、部署和启用是三个独立确认

- 第 1 至第 9 步默认只修改本地代码、数据库测试结构和本地预览。
- 本地步骤通过不代表允许部署到新加坡。
- 部署到新加坡不代表允许启用真实邮件收发。
- 南京服务器 `175.27.225.156` 始终为禁止写入目标，除非用户以后另行明确授权。
- 对新加坡进行任何远程写操作前，必须再次核对公网 IP、SSH 用户、应用目录、
  systemd 服务、数据库、附件目录、备份目录和当前版本。

### 2.3 每一步的完成标准

每一步必须同时具备：

1. 只包含本步骤范围的代码或文档变更。
2. 数据库迁移可重复执行，并保留旧数据兼容性。
3. 服务层、页面、GET/POST/API 和附件下载使用同一权限规则。
4. 针对性测试通过。
5. 完整 `npm test` 通过；如有既存失败，必须证明与本步骤无关并取得确认。
6. `git diff --check` 通过，`git status --short` 已复核。
7. 可见页面完成中英文浏览器验收。
8. 形成范围明确的 Git 检查点，不夹带无关用户文件。
9. 报告修改内容、测试结果、残余风险、回退方法和生产影响。

### 2.4 密码与密钥

- 不读取、不显示、不猜测 NetEase 邮箱授权密码、用户密码或 `.pem` 私钥。
- 密码由用户在私密终端或供应商界面输入。
- 凭据不进入 Git、数据库、日志、截图或聊天记录。

## 4. 分阶段实施步骤

## 第 1 步：固化本地基线与双语基础

### 修改范围

- 复核并完成登录后侧栏 `English / 中文` 切换。
- 保证切换语言后返回当前页面，而不是丢失正在查看的商机。
- 给后续新模块建立统一翻译键命名规则和缺失翻译测试。
- 将本综合设计和本行动指南作为独立文档纳入范围。
- 不修改询价、商机、报价和邮件业务逻辑。

### 验收

- 登录页、工作台、客户、联系人、询价、商机、系统管理均可切换语言。
- 当前 URL 和筛选条件在切换后保留。
- 未登录用户不能通过语言路由获得受保护页面。
- 针对性路由测试和完整测试通过。
- 浏览器展示中英文侧栏和至少一个业务页面。

### 确认门

交付后停止，等待：`确认第1步，开始第2步`。

## 第 2 步：所有新商机统一经过询价

### 修改范围

- 增加销售人员的“提交新线索”简表，不授予询价目录权限。
- 记录来源渠道、客户/联系人、需求、产品、附件和提交人。
- 销售只能查看自己提交后的回执状态，不能浏览询价详情目录。
- 销售经理完成查重、客户确认、销售负责人分配和询价转商机。
- 增加销售经理“快速处理”，但仍在同一事务中建立询价和转换审计。
- 阻断销售人员直接通过页面或 JSON API 创建真实商机。
- 现有商机往来和补充需求不重新生成询价。

### 权限矩阵

| 操作 | 销售 | 销售经理 | 管理员 |
| --- | --- | --- | --- |
| 提交自己的新线索 | 允许 | 允许 | 允许 |
| 查看询价目录/详情 | 禁止 | 允许 | 允许 |
| 查重、分配、转商机 | 禁止 | 允许 | 允许 |
| 绕过询价新建真实商机 | 禁止 | 禁止 | 仅审计修复工具，不提供普通 UI |

### 验收

- 菜单、服务、GET、POST、JSON API、附件访问都执行相同权限。
- 销售直接访问询价 URL 返回拒绝，不能通过构造 POST 绕过。
- 一个线索只能转换一次，并保留来源和经理决定。
- 重复客户、重复邮件和重复平台编号不会重复创建商机。
- 全角色浏览器流程及完整测试通过。

### 确认门

## 第 3 步：商机工程协作角色

### 修改范围

- 每个商机设置且只能设置一名项目主任工程师。
- 一个商机可增加多名协助工程师。
- 支持按商机分配协助工程师的章节、任务和到期日。
- 记录新增、移除、角色变更和实际贡献人。
- 主任工程师整合并提交技术方案；协助工程师默认不能最终提交。
- 协助工程师默认只能起草对外邮件，单独授权后才可直接发送。

### 验收

- 同一人员可在不同商机承担不同工程角色。
- 移除工程成员后立即失去商机、文件和邮件访问权，但历史署名保留。
- 只有主任工程师可以提交完整技术方案。
- 直接 URL、附件和发送接口不能绕过权限。
- 角色矩阵、审计历史和完整测试通过。

## 第 6 步：技术方案版本、审批和文档输出

### 修改范围

- 输出带 SUNKAIER 品牌、文档编号、页码、版本和审批信息的 DOCX/PDF。
- 对输出文件计算校验和并绑定到技术方案版本。

### 验收

- 已批准版本内容和文件不可编辑或删除。
- DOCX/PDF 的关键字段、版本、表格和分页通过视觉检查。
- 中英文输出无缺字、乱码、越界或错误字体替换。
- 退回、修订、重提和历史查看完整可追溯。

## 第 7 步：完整报价包 V1、V2 版本管理

### 修改范围

- 一个报价包绑定准确的技术方案版本、商务报价、条款和附件。
- 内部草稿使用 `QP-D1`、`QP-D2`；正式对客版本使用 `QP-V1`、`QP-V2`。
- V2 从 V1 克隆，必须填写修改原因和客户可读的变更摘要。
- 增加价格、交期、付款、有效期、条款和附件的版本差异比较。
- 已发送、已替代和已接受的报价包不可覆盖或删除。
- 成单时必须明确记录客户接受的报价包版本。

### 验收

- 技术版本未批准时，报价包不能提交或发送。
- V2 发出后 V1 显示“已替代”，但全部内容、文件和历史仍存在。
- 客户接受版本与合同/订单明确关联。
- 版本并发、重复编号、直接修改和删除均被数据库及服务层阻断。
- 完整版本流程及完整测试通过。
