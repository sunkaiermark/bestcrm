## 1. 实施目标

按照已冻结的《BESTCRM 标书中心 V1 设计规范》，在现有 CRM、技术模板、技术方案、商务报价和报价包版本能力上增量建设：

1. 真正的商务包模板库和标准商务条款。
2. 技术、商务和通用内容组件库。
3. 每个商机一个主标书工作区。
4. 技术包和商务包项目副本、结构化编辑和差异追踪。
5. 技术、商务和完整标书的分层审批。
6. 技术包、商务包、完整标书 DOCX/PDF、附件 ZIP 和 manifest。
7. 不可变正式版本、发送归档、权限、审计、备份和回滚。

本计划只规定实施顺序、文件边界、测试和确认门。业务含义以冻结规范为准。

## 2. 强制执行规则

### 2.1 一次只实施一个步骤

- 每次只执行一个步骤，不提前修改后续步骤的代码。
- 每一步完成后停止，报告修改文件、测试、风险和 Git 检查点。
- 只有用户确认当前步骤后，才能进入下一步。
- 用户在验收中提出调整时，只修正当前步骤并重新验证。

### 2.2 设计、实施、部署、启用分别确认

- 冻结设计已经确认，但不等于批准全部代码一次性实施。
- 本计划确认后，才开始第 0 步。
- 第 0 至第 7 步默认只在独立本地工作树实施和验证。
- 第 8 步暗部署必须单独确认。
- 暗部署完成不等于启用；打开 `BID_CENTER_ENABLED` 必须再次确认。
- 南京旧服务器和其他项目服务器不在本计划范围内。

### 2.3 独立工作树和提交边界

- 不在当前脏 `master` 工作树直接实施。
- 从当前生产提交 `cb06575742542a8ffb7ea116e22442d05e63f2cb` 创建独立分支和工作树。
- 将冻结设计提交 `18960aa31d597f665361e095c0f5d3cf30ce7797` 引入实施分支。
- 当前本地未部署的“技术包 / 商务包”菜单改名不直接复制；按冻结导航重新实现。
- 每一步只提交该步骤的精确文件，提交前检查暂存区和工作树。
- 不覆盖或删除主工作树中的用户文件、设计稿、图片、发布包或其他未提交修改。

### 2.4 固定完成标准

每一步必须同时满足：

1. 修改范围与本步骤一致。
2. 中英文词典同步。
3. 数据迁移可重复执行，现有数据兼容。
4. 导航、GET、POST、API、预览和下载使用同一服务层权限。
5. 定向单元、服务、路由和数据库测试通过。
6. 完整 `npm test` 通过。
7. `git diff --check` 通过。
8. 真实浏览器验证桌面和移动布局。
9. 文档输出步骤必须实际渲染并检查 DOCX/PDF 页面。
10. 建立只包含本步骤内容的 Git 检查点。

### 2.5 数据和文件安全

- 不使用真实客户敏感数据作为自动化测试夹具。
- 历史标书进入开发环境前先脱敏。
- 商务价格、付款、合同和附件遵循服务器端权限。
- 发布模板、批准项目版本、已发送客户版本和生成文件不可原地修改。
- 文件只能通过授权路由访问，不创建公开静态 URL。
- 任何删除、覆盖、生产迁移、部署或功能启用都遵循独立确认门。

## 3. 第 0 步：样本、输出样式和验收基准

## 6. 第 3 步：商务模板、标准条款和公共资料库

- 商务模板结构化章节编辑器。
- 内容组件按 `technical`、`commercial`、`common` 分类。
- 标准技术条款、标准商务条款和通用条款筛选。

## 8. 第 5 步：技术包与商务包项目编辑器

### 目标

实现可按项目修改、可恢复标准内容、可分工、可查看差异的双包编辑体验。

### 修改范围

- 左侧章节目录、完成状态和责任人。
- 中间正文、表格、变量、图片和附件编辑。
- 右侧模板来源、条款、变量来源、差异和审批意见。
- 章节状态：`standard`、`customized`、`project_added`、`omitted`、`needs_review`。
- 支持新增、修改、删除可选章节、重新排序和恢复到项目模板快照。
- 支持条款增删和公共资料选择。
- Supporting Engineer 只能编辑被分配的技术章节。
- 项目修改可发起“建议纳入模板库”，只创建新的内容或模板草稿。
- 所有保存写入 `bid_section_changes` 和审计事件。

### 验收

- 项目编辑不改变任何模板或其他项目。
- 可以看到逐章节标准内容和项目内容差异。
- 恢复标准内容只恢复当前项目章节。
- 商务价格和合同字段不会暴露给仅有技术协作权限的用户。
- 页面刷新和重新登录后，编辑内容、顺序、附件和状态保持一致。
- 桌面与移动浏览器操作可用。

### 确认门

## 9. 第 6 步：完整性检查和分层审批

### 目标

把技术、商务和完整标书的提交、退回、批准和版本关系接入现有工作流。

### 修改范围

- 技术包继续使用 `TS-Dn`、`TS-Vn` 和 Technical Manager 审批。
- 商务包增加 `CP-Dn`、`CP-Vn` 和 Commercial Manager 审批。
- 完整标书使用 `QP-Dn`、`QP-Vn` 和现有报价包审批/发送流程。
- 提交前执行冻结规范第 14 节完整性检查。
- 退回时保留被退回快照并创建下一草稿。
- 新正式版本必须从当前已发送版本克隆，填写内部原因和客户可读摘要。
- 版本比较覆盖字段、章节、条款、公共资料和附件哈希。
- 工作流待办、通知和时间线记录准确收件人和实际操作人。

### 验收

- 缺失必填变量、未处理偏差、金额不一致或缺少附件时不能提交。
- 技术未批准时不能批准完整标书；商务未批准时同样被阻止。
- Administrator 不能代替 Technical Manager 或 Commercial Manager 正常审批。
- 已批准和已发送版本不可修改或删除。
- 直接 POST、API 和重放请求不能绕过状态和角色检查。

### 确认门

完成后停止，等待：`确认第6步，开始第7步`。

## 11. 第 8 步：完整本地验收和发布候选

### 目标

在不修改生产的情况下完成端到端业务、权限、文档和回退验证。

### 端到端场景

1. 从商机创建项目标书。
2. 选择技术、商务模板和双语输出样式。
3. 自动预填数据并人工修改项目内容。
4. 分派技术章节并完成协作。
5. 提交和批准技术包。
6. 提交和批准商务包。
7. 装配、审批并生成 `QP-V1`。
8. 下载技术、商务、完整标书和附件 ZIP。
9. 创建 `QP-V2`，比较变化并保留 `QP-V1`。
10. 验证未授权人员不能读取商务内容或下载附件。

### 验收

- 全量测试全部通过。
- 真实浏览器桌面和移动流程通过。
- 所有文档完成逐页渲染检查。
- 数据库备份和恢复演练包含新增表和文件。
- 功能关闭时现有生产行为无变化。
- 形成不可变提交、候选标签、发布包和 SHA-256。
- 发布报告列明迁移、运行时配置、回退和残余风险。
