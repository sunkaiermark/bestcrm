# BESTCRM 登录与 MFA 结构重构计划 V1（待确认）

日期：2026-09-05

状态：规划草案，尚未实施

依据：已冻结的《BESTCRM Authenticator MFA V1 设计规范》

## 1. 目标

在不改变现有登录行为、安全策略、数据库结构和管理员试点范围的前提下，降低登录与 MFA 代码的复杂度，使后续维护、审计和扩展更安全。

当前主要结构热点：

- `src/routes/authRoutes.mjs` 同时承担密码登录、MFA 判断、绑定、验证、恢复码、信任设备、会话和页面响应等多类职责。
- `src/server.mjs` 的应用装配逻辑较集中，认证依赖与空实现适配器不易独立验证。
- 多条认证失败路径分别处理审计、次数限制、会话清理和重定向，未来修改容易出现行为偏差。

## 2. 必须保持不变的行为

本次重构只调整内部结构，下列冻结规则不得改变：

- 密码始终是第一道验证，不能使用 TOTP 或信任设备绕过密码。
- TOTP、恢复码和信任设备令牌的现有语义保持不变。
- 待验证登录会话有效期保持 5 分钟。
- MFA 连续失败 5 次后的现有锁定规则保持不变。
- 信任当前设备保持固定 10 天，不采用滑动续期。
- TOTP 密钥继续使用 AES-256-GCM 加密保存。
- 恢复码继续采用不可逆摘要、一次使用即失效的机制。
- 登录成功时继续执行会话 ID 更新、CSRF 防护、权限装载和安全审计。
- 不记录 TOTP 密钥、二维码内容、动态码、恢复码或完整信任令牌。
- 短信 MFA 保持关闭。
- 当前仅管理员试点的生产策略不扩大。

## 3. 非目标

- 不更换加密算法或 TOTP 库。
- 不重新设计登录页面视觉样式。
- 不增加微信登录、短信验证、邮箱验证码或单点登录。
- 第一阶段不做数据库迁移。
- 不在结构重构过程中同时改变密码策略、角色模型或会话有效期。

## 4. 目标结构

### 4.1 路由层

保留一个统一的 `authRoutes.mjs` 装配入口，但将具体路由拆成职责明确的模块：

- `passwordLoginRoutes.mjs`：登录页、密码校验和第一阶段登录。
- `totpChallengeRoutes.mjs`：动态码、恢复码和信任设备验证。
- `totpEnrollmentRoutes.mjs`：首次绑定、确认启用和恢复码确认。
- `authSessionRoutes.mjs`：退出登录及认证会话收尾。

路由层只负责输入解析、调用用例、HTTP 响应和错误映射，不直接编排密码学细节或跨步骤状态。

### 4.2 应用服务层

- `authenticationOrchestrator.mjs`：根据用户状态、MFA 策略和设备状态决定下一步登录阶段。
- `pendingAuthenticationService.mjs`：统一创建、读取、计数、过期和销毁待验证登录状态。
- `mfaChallengeService.mjs`：统一 TOTP、恢复码、失败次数和验证结果。
- `mfaEnrollmentService.mjs`：统一首次绑定、密钥激活和恢复码确认。

### 4.3 HTTP 辅助层

以 `authRouteHelpers.mjs` 或 `authRequestContext.mjs` 集中处理：

- IP、User-Agent 和请求时间等审计上下文。
- 登录后的安全跳转地址。
- 页面渲染所需的公共字段。
- 安全一致的认证错误响应。

不得把安全决策放进视图辅助函数。

### 4.4 领域决策

使用可测试的显式结果表示认证状态，例如：

- `PASSWORD_REJECTED`
- `MFA_NOT_REQUIRED`
- `MFA_ENROLLMENT_REQUIRED`
- `MFA_CHALLENGE_REQUIRED`
- `TRUSTED_DEVICE_ACCEPTED`
- `MFA_LOCKED`

状态名称是内部建议，实施前可调整；外部 URL、页面字段和用户可见行为默认保持不变。

## 5. 分阶段实施

### 第 0 阶段：行为基线与安全决策表

- 列出密码正确/错误、MFA 启用/未启用、已绑定/未绑定、设备可信/不可信、恢复码有效/无效等组合。
- 为每个组合记录预期页面、状态码、会话变化、审计事件和重定向。
- 补齐特征测试，先固定现状，再移动代码。

验收：所有现有认证测试通过，决策表中的关键组合均有自动化覆盖。

### 第 1 阶段：提取纯辅助函数

- 提取请求上下文、重定向校验、页面公共数据和无副作用格式化逻辑。
- 不改变路由数量、数据库调用顺序和会话语义。

验收：差异只涉及函数移动及等价调用；登录与 MFA 回归测试全部通过。

### 第 2 阶段：集中待验证登录状态

- 将待验证会话的创建、过期、尝试次数和销毁集中到一个服务。
- 明确每个成功、失败、超时和取消路径的清理规则。

验收：5 分钟有效期、5 次失败限制、会话固定攻击防护均保持不变。

### 第 3 阶段：拆分绑定与挑战流程

- 将 MFA 首次绑定和日常验证从主路由工厂拆出。
- 将 TOTP、恢复码和信任设备的结果统一映射为显式决策结果。

验收：绑定二维码、手工密钥、动态码、恢复码、信任 10 天及退出后的行为与冻结规范一致。

### 第 4 阶段：统一失败处理和审计

- 集中认证失败计数、锁定、审计事件和敏感字段清理。
- 保持现有事件名称；若确需调整，另立兼容方案并单独确认。

验收：每条失败路径只产生预期审计记录，不泄漏秘密，不重复计数。

### 第 5 阶段：简化应用装配

- 将认证相关依赖组合成明确的认证模块接口。
- 缩小 `createApp` 中认证装配和空适配器代码。
- 不改变生产环境变量名称或启动方式。

验收：功能关闭、管理员试点和全量关闭三种配置均能正常启动并符合预期。

### 第 6 阶段：安全回归、暗部署与试点复核

- 执行 ESLint、全量单元/集成测试和认证专项测试。
- 在受控环境执行密码登录、首次绑定、TOTP、恢复码、信任设备、退出登录和过期场景的浏览器验证。
- 先暗部署，保持当前试点范围；经人工验收后再切换正式版本。

验收：健康检查正常、管理员试点成功、非试点用户行为不变、可使用前一不可变版本回滚。

## 6. 质量门槛

- ESLint 错误为 0。
- 路由工厂目标控制在 150–200 行以内。
- 单个处理函数目标不超过 120 行。
- 认证处理函数圈复杂度目标不超过 15。
- 关键安全决策必须有正向、反向和过期测试。
- 不因重构新增重复实现；审计、会话清理和错误映射应各有单一入口。
- 数据库结构、生产环境变量和外部 URL 如需改变，必须另行设计和审批。

## 7. 发布与回滚边界

- 每个阶段独立提交、独立测试，不与标书中心重构混合。
- 本地验证通过后才能制作不可变发布包和校验哈希。
- 暗部署时保持 MFA 当前开关和管理员试点名单不变。
- 切换前自动备份；切换失败或认证专项检查失败时立即恢复上一版本。
- 任何扩大 MFA 用户范围的操作都需要单独确认。

## 8. 实施前确认项

只有本计划确认后才进入第 0 阶段。第 0 阶段只建立行为基线和测试，不移动生产逻辑。
