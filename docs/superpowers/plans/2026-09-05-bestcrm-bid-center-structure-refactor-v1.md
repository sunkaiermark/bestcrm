# BESTCRM 标书中心结构重构计划 V1（待确认）

日期：2026-09-05

状态：规划草案，尚未实施

依据：已冻结的《BESTCRM 标书中心 V1 设计规范》

## 1. 目标

在不改变标书中心 V1 的业务规则、权限、版本、审批和输出结果的前提下，降低技术包、商务包和完整标书之间的重复代码，拆分过大的路由、服务、仓库和模板，建立可持续维护的模块边界。

当前静态扫描基线：211 个文件、38,268 行中识别到 98 处克隆片段，重复行约 1,486 行，占 3.88%。其中 JavaScript 约 3.30%，模板标记约 7.34%。扫描结果只是候选清单，不能直接批量合并；部分相似代码承载不同权限或版本语义。

## 2. 必须保持不变的业务规则

- 每个商机只有一个主标书工作区。
- 技术包、商务包和完整标书保持独立状态与审批边界。
- 已发布、已审批和已发送的版本保持不可变。
- 项目内容可以从模板复制后修改，但不得反向污染标准模板。
- 模板、内容块、章节和项目快照的版本号及追溯关系保持完整。
- 菜单、页面、服务、接口、下载和审批均继续执行服务端权限校验。
- 文档输出继续保留来源版本、生成时间、文件元数据和哈希。
- 技术包与商务包的可见范围、可编辑范围和审批权限不扩大。
- 现有 URL、表单字段和导航名称默认保持不变。

## 3. 非目标

- 第一阶段不改变数据库表结构。
- 不重新设计冻结的标书业务流程。
- 不在结构重构中加入 AI 自动编写、自动审批或自动发送。
- 不用一次大改替换全部仓库、路由和模板。
- 不把技术包和商务包强行合并成一个失去业务语义的通用对象。
- 不在同一发布中实施登录/MFA结构重构。

## 4. 目标结构

### 4.1 领域策略层

建议建立 `src/domain/bid-center/`，集中放置不依赖 HTTP 和数据库的规则：

- `packageTypes.mjs`：技术包、商务包、完整标书等受控类型。
- `packageStatusPolicy.mjs`：允许的状态与状态转换。
- `bidAuthorizationPolicy.mjs`：查看、编辑、提交、审批、导出和下载决策。
- `revisionInvariants.mjs`：不可变版本、编号连续性和快照一致性规则。

权限策略输出明确的允许/拒绝及原因，但最终服务端强制执行仍位于应用服务入口。

### 4.2 应用用例层

建议建立 `src/application/bid-center/`，按用例组织：

- 模板发布与修订。
- 项目包初始化与内容编辑。
- 技术包、商务包和完整标书的提交与审批。
- 快照生成与文档输出。

共性通过明确的组件复用，而不是通过大量布尔参数形成“万能服务”。

### 4.3 可复用组件

- `revisionLifecycleService.mjs`：草稿、发布、复制修订和不可变检查。
- `snapshotMapper.mjs`：将模板、项目内容和审批状态转换为稳定快照。
- `contentSchemaMapper.mjs`：内容块序列化、反序列化和版本兼容。
- `bidAuthorizationPolicy.mjs`：统一菜单以下各层的权限判断。
- `documentManifestService.mjs`：统一输出文件名、元数据、哈希和来源版本。

“复用”必须保留技术包与商务包的业务差异；差异通过清晰策略或专用适配器表达。

### 4.4 数据访问层

在不改表结构的前提下，将过大的仓库按聚合或读写职责拆分：

- 模板查询与模板修订命令。
- 项目包查询与项目包命令。
- 内容块查询与内容块命令。
- 审批、快照和输出记录。

事务边界由应用用例控制，避免跨仓库调用后出现半完成状态。

### 4.5 路由与视图层

- 路由按模板、项目工作区、审批和输出资源拆分。
- 路由只处理输入、权限入口、用例调用和 HTTP 响应。
- 将重复的标题区、状态条、操作栏、表单字段、预览面板和错误提示提取为 EJS partial。
- 不为了减少模板重复而隐藏重要的技术包/商务包差异。

### 4.6 文档输出流水线

将输出过程拆成可独立验证的阶段：

1. 构建冻结的文档规格对象。
2. 校验章节、字段、附件和审批条件。
3. 渲染 DOCX/PDF。
4. 写入受保护的制品目录。
5. 计算哈希并登记 manifest。

渲染器不得自行查询变化中的业务数据，确保同一快照能够稳定复现。

## 5. 分阶段实施

### 第 0 阶段：重复代码分类与黄金基线

- 逐项审阅 98 处克隆候选，标记为“应合并”“业务相似但应独立”“测试夹具重复”“生成产物忽略”。
- 建立关键页面、权限矩阵、版本流转和文档输出的黄金基线。
- 保存代表性 DOCX/PDF 的结构、页数、关键文字、文件元数据和来源哈希。

验收：形成可审核的重复清单；任何后续合并都能对应到明确候选和测试。

### 第 1 阶段：提取纯映射与规范化函数

- 先处理无数据库副作用的内容结构、快照、字段和文件名映射。
- 为技术包与商务包差异建立显式测试。

验收：序列化结果和页面数据结构不变，所有黄金测试通过。

### 第 2 阶段：集中权限与业务不变量

- 统一查看、编辑、提交、审批、导出和下载的权限决策。
- 将不可变版本、状态转换和主工作区约束集中为领域策略。
- 保留路由、服务和文件下载的纵深防御，不仅依赖菜单隐藏。

验收：角色权限矩阵及直接访问测试全部通过，未授权用户不能通过 URL 绕过。

### 第 3 阶段：复用修订生命周期

- 识别技术模板、商务模板、内容块和项目副本共有的修订操作。
- 通过受控接口复用草稿、发布、复制、快照和不可变检查。
- 特定包类型的验证规则留在专用策略中。

验收：版本号、来源链、发布时间和历史只读行为不变。

### 第 4 阶段：拆分大型路由、服务和仓库

- 按业务用例逐个拆分，不一次移动全部模块。
- 每次只迁移一条完整调用链，并保持原接口兼容层，确认稳定后再移除旧入口。
- 明确应用服务事务边界和审计责任。

验收：不存在双写或半完成记录；原有 URL、状态码和错误语义保持兼容。

### 第 5 阶段：提取视图公共组件

- 提取经确认真正一致的 EJS partial 和视图模型。
- 对技术包、商务包、完整标书分别执行桌面和窄屏视觉回归。

验收：操作按钮、状态提示、字段顺序、权限可见性和中文文案不变。

### 第 6 阶段：重构文档生成流水线

- 将规格构建、校验、渲染、制品写入和 manifest 登记解耦。
- 渲染过程只消费冻结快照。
- 为代表性技术包、商务包和完整标书执行 DOCX/PDF 黄金比较。

验收：输出内容、章节顺序、页眉页脚、附件关系、文件名、来源版本和哈希登记正确。

### 第 7 阶段：全量回归、暗部署与启用确认

- 执行 ESLint、全量测试、数据库集成测试、权限直接访问测试和浏览器视觉检查。
- 验证生产备份、不可变发布包、哈希、原子切换和回滚。
- 暗部署后保持当前功能开关，不自动扩大可见范围。

验收：健康检查、关键流程、文件生成与下载均正常；获得单独确认后才正式启用重构版本。

## 6. 质量门槛

- ESLint 错误为 0。
- JavaScript 重复率阶段目标低于 2.5%。
- 模板标记重复率阶段目标低于 4%。
- 第一轮拆分后单个工厂目标不超过 300 行，后续目标不超过 200 行。
- 业务处理函数圈复杂度目标不超过 15。
- 每一处抽象必须至少由两个真实用例证明，禁止为“看起来通用”提前抽象。
- 不降低权限、审计、版本追溯和输出一致性的测试覆盖。
- 如果必须改变数据库结构，停止当前阶段，另行提交迁移设计、备份和回滚方案审批。

## 7. 发布与回滚边界

- 与登录/MFA重构使用不同分支、不同提交和不同发布窗口。
- 每个阶段先本地测试，再进入测试环境或暗部署。
- 发布包必须不可变并校验 SHA-256；切换前自动备份数据库和上传/输出制品索引。
- 保留上一版本和兼容接口，关键检查失败立即回滚。
- 不在未经确认的情况下删除旧模板、旧修订、旧输出文件或历史记录。

## 8. 实施前确认项

只有本计划确认后才进入第 0 阶段。第 0 阶段只分类重复代码并建立黄金基线，不重构生产逻辑、不改变数据库、不部署。
