## 1. 执行目标与边界

建立独立的“新产品开发”模块，让客户非标需求、既有产品升级、内部创意和实施反馈成为可追踪的研发课题；在低成本探索阶段进行多方讨论，经过概念方案门槛才进入正式详细设计。课题保存调研、竞品/专利分析、试验原始数据、讨论、决策和失败教训；商机保留对客方案及当时所引用的已审核结论版本。一个课题可关联多个商机，一个商机也可关联多个课题。

本期不把研发课题伪装成商机或产品分类，不自动生成客户方案，不把内部原始研究资料暴露到商机，不实现 CAD/PDM/PLM 文件权威管理，也不包含 Google Drive 迁移。三个产业方向“工艺技术／关键设备／实施支持”可多选，它们不是现有的固定产品类别。

流程门槛参考 [ISO/IAF 的设计开发分阶段评审与记录指导](https://committee.iso.org/files/live/sites/tc176/files/documents/ISO%209001%20Auditing%20Practices%20Group%20docs/Auditing%20to%20ISO%209001%202015/APG-Design%26Development2015.pdf)；这里采用适合胜开尔的轻量阶段门控，不宣称增加认证义务。技术资料沉淀、检索和复用的方向可参照 [NIST 的数字线程资料管理思路](https://www.nist.gov/programs-projects/digital-thread-smart-manufacturing)。

## 2. 顺序与批准门

| 阶段 | 交付物 | 放行条件 |
| --- | --- | --- |
| P0 业务规则审核 | 本文、状态/权限/证据字典、页面与接口草图 | 用户确认进入下一实施阶段所必需的规则；变更冻结框架需另行确认 |
| P1 数据底座 | 独立课题、成员、关联、不可覆写的修订/事件及迁移测试 | 新课题无需商机；双向多对多；原始历史可追溯 |
| P2 概念门控 | 探索、方案修订、送审、技术经理决策、回退与暂停 | BESTCRM 前后端/API 阻止未批准的正式设计交接；未来产品工程还须在自身命令端再次校验；并发与重复提交安全 |
| P3 资料与结论 | 研究附件、哈希、保密级别、试验记录、结论版本 | 内部研究与对客资料隔离；文件/数据库一致；失败资料不丢 |
| P4 业务关联与界面 | 课题总览、课题五区、技术资产库、商机内引用入口 | 仅展示有权且已审核的精确版本，不改写已交付的对客版本 |
| P5 验证与交付审查 | 自动测试、权限攻击用例、备份恢复演练、预览 | 用户验收后再决定提交/发布；本计划不授权上线 |

每一阶段单独交付供审查；不要把未通过的后阶段功能与前阶段一起发布。P0 是设计批准门，不等于后续部署批准。实现前必须重新核对线上活跃版本、当前仓库提交与工作区状态，证明本地基线与线上一致；若不一致，先停下并报告差异，不在旧代码上叠加功能。

## 3. 业务流程与状态机

### 3.1 课题阶段与结果分开

建议的课题阶段：`idea`（提出）→ `exploration`（探索）→ `concept_review`（概念待审）→ `detailed_design`（详细设计）→ `verification`（验证）→ `concluded`（结论）。`paused` 和 `stopped` 是受控分支，需记录原因；两者恢复均回到记录的原阶段，不允许页面任意跳跃。最终结果另存为“成功／部分成功／失败／未定”，不从阶段自动推导。暂停、终止、恢复的申请及管理员批准规则见 P2 政策修订。

概念方案的有效决定为 `approved`、`revise_required`：每次送审锁定一份不可变快照，技术经理对**该具体修订**作出有时间戳的决定；只有 `approved` 可以开启正式详细设计。暂停、终止、恢复改由课题负责人申请、管理员审批的独立生命周期记录处理，不能混作概念修订决定。评审意见和未采纳方案也保留。销售、工艺、设备、实施人员的意见属于协作证据，不构成审批会签。

### 3.2 门控的可执行规则

1. 送审前要求一页式概念包：问题/应用场景、候选方向及取舍、关键假设、已知风险、探索证据、预估下一步投入、与商机/客户的关系（若有）。不要求完整图纸、计算书或 BOM。
2. 探索阶段允许必要的低成本计算、小试、草图或样机，记录为 `exploratory`；这些材料不能被标为已批准正式设计，也不能作为已验证对客成果发布。
3. **新产品开发模块只发放有精确修订号的正式设计交接资格，不在 BESTCRM 内创建产品工程权威记录。**BESTCRM 后端阻止未批准的交接；未来产品工程在创建正式设计、启动任务、发布受控设计资料或签发验证时，必须由自己的后端再次核对当前有效的已批准概念修订。隐藏按钮不算门控。技术经理的审批动作亦由新产品开发服务层验证角色、课题可见性和被审修订号。
4. 被要求修改时形成下一概念修订；旧修订与旧决定只读。关键方向、关键假设或适用范围改变时，撤销“继续沿用旧批准”的资格并再次送审；普通编辑不悄悄改变已批准快照。
5. 中止/失败只终止推进，不删除研究、试验、讨论、决定或客户已交付版本。失败结论可进入“经验教训”候选区，但不能自动变为可复用成熟技术。
6. 审批采用事务和乐观并发控制：只批准调用时指定且仍为当前送审版本的修订；过期版本或双击重复请求返回冲突/已有结果，不产生两个有效批准。

### 3.3 评审职责（已确认与待确认）

- 已确认：**仅技术经理**能作概念方案进入详细设计的最终批准；不能因为用户是销售经理、一般管理员、课题创建人或商机负责人就放行。若某人同时具有技术经理身份，应按其技术经理权限判定，记录实际操作者。
- 建议：课题负责人负责整合概念包；被邀请成员可评论、上传有权材料；销售可确认客户问题与商业背景，但不是审批必经人。
- 已确认：技术经理可以批准本人编写或提交的概念包，但须记录独立自审理由。缺席时仅能由另一位在职技术经理代理指定课题，管理员记录任命与期限，不能自行代签；详见 P2 政策修订。
- 已确认：指定的结论/经验修订进入技术资产库，须由**另一位在职技术经理且为该课题有效成员**独立审核；修订编写/提交者不得自审，也不得设置缺席代理。没有合格审核人时保持待审核，不由管理员代签。概念方案批准与资产发布批准分别操作、分别留痕；发布后是否可直接供商机对客引用仍待确认，不能从发布动作自行推定。

## 4. 领域模型和数据约束

以下是实施级候选模型，P0 审核后才冻结字段、命名和迁移。优先使用 PostgreSQL 约束和事务维持结构，不用仅靠页面逻辑维持安全。

| 对象 | 主要字段/约束 | 用途 |
| --- | --- | --- |
| 研发课题 `development_topics` | 独立 ID、可读编号、标题、来源、问题摘要、阶段、结果、负责人、创建/更新时间、并发版本；不要求 `opportunity_id` | 想法到结论只有一个课题身份 |
| 方向 `development_topic_directions` | 课题 × 三个固定方向，联合唯一 | 多方向检索，不与 CRM 产品类别混用 |
| 成员 `development_memberships` | 课题 × 用户 × 职责、有效期，避免重复有效成员 | 受控协作与可见性 |
| 商机关联 `development_opportunity_links` | 课题 × 商机联合唯一、关联原因/时间/操作者；两个真实外键 | 多对多追溯，非资料权限继承 |
| 概念修订 `development_concept_revisions` | 课题、连续修订号、结构化概念包、送审人/时间、内容快照摘要、只读历史 | 审批的确定对象 |
| 概念决定 `development_concept_decisions` | 修订、决定、理由、技术经理用户、时间、幂等键；一修订至多一个最终决定 | 进入正式设计的审计证据 |
| 研究资料 `development_materials` 与版本 | 课题、类别、密级、来源/引用、上传者、文件元数据、SHA-256、不可变版本、有效/替代关系 | 原始实验、竞品、专利等资料；不能借用必须有商机 ID 的旧附件表 |
| 活动与讨论 `development_events` | 课题、动作/评论、执行人、时间、关联修订/证据 | 记录协作、状态转换及被否决原因 |
| 结论修订 `development_outcome_revisions` | 课题、结果类别、技术结论、适用条件、限制、证据引用、审核/发布状态 | 结论与研究过程分开；后续修订不覆写旧版本 |
| 资产记录 `development_assets` | 指向已发布的精确结论/经验修订、可检索摘要、可见级别、撤回/替代状态 | 资产库只呈现获准复用内容 |
| 业务引用 `development_result_uses` | 结论修订 × 商机 × 对客文件版本（如存在），引用目的/操作者/时间 | 对客使用锁定精确历史版本 |

迁移须包含唯一键、外键、非空/状态检查、查询索引和阻止关键审计行硬删除的约束。编号采用独立前缀；不得消耗 `800XXX` 商机号，也不得与既有产品类别编码冲突。保密资料不能仅靠“隐藏列表项”保护，下载必须重新鉴权。每一状态转移、修订批准、结论发布和业务引用都写审计事件。系统时间统一存 `timestamptz`，展示按用户/系统时区。

既有 `work_items` 有 `technical_project` 业务类型。实现时先核对该类型实际用途与索引/唯一键，再决定是否用它承载研发任务；不得建第二套互相矛盾的工作台，也不得未经审查把研发课题直接当作现有技术项目。研发审批状态由本模块掌握，工作项只承载执行任务。

## 5. 权限、保密与文件存储

### 5.1 最小权限矩阵（提案，P0 核定）

| 动作 | 提案权限 | 强制检查位置 |
| --- | --- | --- |
| 创建课题、编辑未送审概念、参与讨论 | 有新产品开发权限的员工；课题负责人/受邀成员按职责编辑 | 菜单、列表查询、路由、服务、对象级访问 |
| 查看/下载研究原件 | 课题成员且满足文件密级；技术经理在职权范围内 | 列表、详情、下载、预览、直链均检查 |
| 提交概念包 | P2 仅在职课题负责人且为有效成员；未来其他授权需另审 | 服务层校验必填包与当前修订 |
| 批准进入详细设计 | **仅在职技术经理**：有效课题成员或指定任期内的代理；管理员不能代签 | 服务层角色＋对象＋修订/代理期限检查，记录审批人及代理任命 |
| 发起正式设计交接；由未来产品工程创建正式设计任务/受控版本 | P2 仅在职课题负责人且当前概念修订有效批准 | BESTCRM 校验交接；产品工程另行校验其自身命令，不只限于按钮 |
| 申请暂停/终止/恢复 | 在职课题负责人且为有效成员 | 行版本、待决申请及恢复原阶段检查 |
| 批准/驳回暂停、终止或恢复 | 在职管理员；可自批但须写独立理由 | 服务、数据库双重检查，保留不可变决定与审计 |
| 任命/撤销技术经理代理 | 在职管理员记录；代理人必须是另一位在职技术经理 | 课题范围、任期、重叠、撤销与角色实时检查 |
| 发布结论/经验到资产库 | **另一位在职技术经理且为该课题有效成员**独立审核；禁止自审及代理；不能因为概念通过而自动发布 | 服务层在决定时核对角色、有效课题成员资格、作者/提交者分离、指定结论修订与状态，分别记录发布决定和审计 |
| 在商机引用结论 | 同时有该商机访问权、可使用该结论版本的人员 | 两侧对象权限；仅暴露发布摘要及允许的附件 |

客户保密、专利检索资料、竞争分析、原始实验数据至少可区分内部/受限，具体密级与适用人群待确认。关联商机、复制链接或调整成员不自动降低密级。审计日志应记录谁看过/下载过受限文件，敏感内容不写入应用日志。外部 AI 默认不得接收资料/附件。

### 5.2 存储方案

- PostgreSQL 保存课题、关系、修订、审计和文件元数据；文件二进制存于既有受控上传根目录下**独立研发子树**，不存进商机附件目录，也不要求虚构商机。
- 服务端生成存储路径；阻止路径穿越与任意文件读取；限制尺寸、扩展名/MIME，校验实际文件类型并按 SHA-256 记录完整性。显示原始文件名时转义；潜在危险格式默认下载而非内联执行。
- 上传采用临时落盘→完整性校验→数据库事务/元数据提交→原子落位或可恢复补偿；失败不得留下可引用的“孤儿已发布文件”。重传产生新版本而不是覆盖旧二进制。
- 技术资产引用与商机对客文件均锁定精确修订；后续研发变化只能产生新修订/新引用。需保留的客户历史版本不被回写。
- 研发文件、元数据和审计必须纳入现有生产备份与恢复校验；上线前用隔离环境演练恢复。保留时长、最大文件尺寸、病毒扫描方式及 CAD/PDM 未来衔接仍待确定，不在此次方案中伪定。
- 已确认本阶段不在 CRM 保存或在线预览 SOLIDWORKS 原生 `.SLDPRT/.SLDASM/.SLDDRW`；权威工程原件与版本将由未来工程/PDM 系统管理。CRM 可保留获授权的研究说明与必要的 PDF/STEP 等文件；跨系统引用需另定接口，不假设已接通。

专利资料应保存来源、检索日期、检索范围与分析结论；不要把内部分析当作法律上的“自由实施”保证。[WIPO 专利分析资料](https://www.wipo.int/en/web/patent-analytics)可作为资料整理参考，但正式法律判断需另行授权。

## 6. 页面和接口契约

页面：侧栏“新产品开发”→“课题总览”和“技术资产库”；课题详情保留冻结的五区：基础研究、开发与验证、协作与决策、结论与版本、关联业务。首屏清楚显示课题阶段、结果、当前概念修订、是否已批准详细设计、负责人、三个方向与保密提示。送审页先给一页式概念包预览；技术经理批准页必须显示不可变修订号、风险和证据，避免审批时看到被编辑后的内容。商机详情仅加研发结论引用区，不自动展开原始研究文件。

建议 REST 路由契约（最终路径以项目约定为准）：

| 类别 | 操作 | 核心返回/失败语义 |
| --- | --- | --- |
| 课题 | `GET /development/topics`、`POST /development/topics`、`GET /development/topics/:id` | 列表仅返回可访问记录；未知/无权对象不泄露详情 |
| 概念 | `POST /development/topics/:id/concepts`、`POST .../:revision/submit`、`POST .../:revision/decision` | 修订不可覆盖；过期修订 `409`；权限不足 `403`；缺证据 `422` |
| 资料 | 上传版本、列表、受控下载/预览 | 文件读取每次鉴权；大小/类型不合规 `422`；缺失文件不得返回假成功 |

## 9. 当前待确认项与停止条件

1. **利益冲突/代理**：概念方案自审与代理已按 P2 政策修订确认。结论资产发布**不沿用**该规则，须由另一位在职技术经理且为该课题有效成员审核指定修订；禁止作者/提交者自审和缺席代理。没有合格审核人时保持待审核，管理员不得代签技术决定。
2. **保密分级**：客户保密资料、内部研究及通用资产的具体可见角色和对商机展示的摘要边界。

4. **结论适用**：技术经理批准结论进入资产库后，商机对客引用是否还需单独批准？建议分开以控制误用；在明确规则前不开放对客引用。

| BESTCRM 的 CRM销售 | 现阶段的客户、联系人、商机及已发送的对客方案/报价版本 | 原始研究库、正式产品图纸、EBOM、Mixers 选型计算 |

目前不能以目标平台的规划名义改写 BESTCRM 的现有客户数据主责。将来统一伙伴身份与 CRM 客户业务属性如何映射，须经单独的数据治理和迁移审核。研发课题、CRM 商机、Mixers 选型案例、精益项目和产品档案各有独立 ID；建立关联，不共用编号或互相自动创建。

### 10.2 独立的批准与交接

1. 新产品开发的概念门槛由**技术经理**批准指定概念修订，只证明该方向可以进入正式设计。指定结论修订进入技术资产库须由**另一位在职技术经理且为该课题有效成员**独立审核，不允许作者/提交者自审或缺席代理；两项决定分别留痕，互不自动替代，也不等于产品工程的图纸/BOM 发布、Mixers 的选型确认或对客报价批准。
2. 在概念批准前，可把 Mixers 中的试算或候选方案作为标明“探索性”的受限证据；不得将其标成已确认技术快照或已批准的客户方案。
3. 获准交接后，产品工程在自身服务中再次校验概念修订，负责正式设计及其权威状态。课题的“详细设计/验证”只作进度追踪；P0 须确认未接入时如何显示。无可用接口时，BESTCRM 仅保存交接资格，不建图纸、EBOM 或 ECN。
4. Mixers 仍按自己的选型确认规则生成不可变技术快照。它可向课题或商机提供被授权的精确版本引用；后续重算必须形成新版本，不追改既有研究结论或已发送的客户文件。Mixers 的计算报价快照与 CRM 正式对客报价是不同对象。

### 10.3 集成数据与交付顺序

跨系统关联记录至少标识来源系统、对象类型、源 ID、版本/修订、状态、确认时间和适用的文件 SHA-256；外部 ID 不得当作本系统主键。研究原件、客户保密材料与竞品/专利原始资料不随引用自动复制或开放。受权查询/下载使用版本化 API；已发生的状态事实可用有幂等、重试与审计的事件传递。不得直接跨系统写表，也不得用共享磁盘路径作为长期接口。

P1→P5 只实现 BESTCRM 内的研发课题、概念门控、资料/结论和已有商机关联。精益管理或 Mixers 的实际对接、统一身份迁移、正式设计命令联动及客户报价同步，必须另列契约、权限和回滚方案，经审核后分期实施；本修订不授权这些工作。Codex 在编码前应先核对目标平台的业务域文档和 Mixers 的现行代码；若主责、审批人、版本语义或接口未确认，停止相应集成，不以复制表或临时脚本绕过。

### 10.4 补充验收

- 未批准概念不能产生正式设计交接；获批后也不能自动发布产品工程图纸/BOM、确认 Mixers 选型或发送报价。
- 在单独批准的 Mixers 对接阶段，同一课题可以引用明确版本的探索记录或已确认快照，但“探索”与“已确认”在页面、API 和历史记录中不可混淆；换版不追改旧引用。

- 跨系统对接阶段须证明对象映射唯一、双向权限、版本/哈希完整、重复事件幂等、失败可重试和历史可追溯；在该阶段获单独批准前，这些属于契约验收要求，不冒充 P1→P5 已完成功能。

## 11. 2026-09-27 技术资产与商机引用的确认规则

本节覆盖上文第 4、6、8、9 节中“对客引用规则待确认”的旧表述，但不改变文件原件、产品工程、Mixers 和已发送客户文件的既定边界。

1. 已由另一位在职且为课题有效成员的技术经理独立审核的结论，须再单独发布到内部技术资产库。发布记录和撤回记录不可覆写。先保守上线：**已发布摘要仅供该课题当前有效成员检索**；管理员、商机成员或已结束课题资格者均不因此获得可见权。原始研究文件始终维持独立密级及逐文件读取授权。
2. 课题与商机的内部关联要求操作者同时是课题有效成员、当前有该商机访问权；关联本身不复制资料、不授权对客引用。解除关联由仍可访问两侧对象的课题负责人操作，保留历史。
3. 对客使用须另建申请，固定**一个当前有效关联的商机、一条已发布且未撤回的技术结论资产、其不可变结论修订和具体用途**。申请者仍须有两侧对象访问权。只有同时为课题有效成员、可访问该商机的在职技术经理可单独批准或拒绝；决定与理由不可覆写。批准不自动应用于其他商机、其他结论版本或其他用途。
4. 技术经理可记录理由撤销已批准的使用。资产撤回或商机关联结束后，即使原批准记录仍保留，该次引用也立即失效。商机页面仅向仍为课题有效成员且可访问商机者显示有效引用的精确版本、适用条件、限制和批准用途；不得以商机访问权绕过课题资料权限。
5. **对客文件版本规则（2026-09-27 确认）**：技术经理的批准只锁定“商机＋不可变结论修订＋具体用途”，不等于结论已经写入或发送给客户。实际用于客户方案时，须在该方案冻结并通过 CRM 发送/归档的流程中，另行将这次仍有效的批准绑定到**同一商机的一份不可变方案文件版本及其 SHA-256**；若是正式报价包，还要记录对应 `quotation_package_versions.id`，并以归档的出站邮件/附件版本作为交付证据。未完成版本绑定的申请只能显示为“已批准使用”，不能显示为“已在对客文件中使用”。绑定后只读；后续结论修改、资产撤回或用途变化须新建批准及新方案版本，不追改已发送文件，也不自动开放研究原件。
6. 本阶段不自动生成、改写或发送客户方案，也不将研发批准当作产品工程图纸、Mixers 选型或报价批准。**本地代码已实现发送成功后的显式文件版本使用登记，尚未提交或上线**：仅在已有有效批准、不可变文件版本、相同商机、已发送邮件附件及出站 MIME 归档完全匹配时登记，操作者确认结论的具体位置。发送流程本身不自动判断文件语义，也不强制选择研发引用；发布清单必须把“已批准使用”和“已实际用于某份客户文件”明确区分。
