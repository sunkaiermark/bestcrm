# 新产品开发 P1：数据字典与迁移审查

状态：本地 P1 实施稿；仅建立内部数据底座，不接入菜单、HTTP 路由或生产数据库。依据《BESTCRM 新产品开发执行方案》及已冻结框架。线上基线于 2026-09-27 核对为 `v2026.09.25-02-rc.1`，对应本地 Git 标签。每一阶段须单独交付审查。

## 本阶段边界

- 研发课题是独立对象，创建时不要求商机；编号 `NPD-<独立序列>`，不占用 `800XXX` 商机号。
- 三个固定产业方向是课题标签，不写入 CRM 产品分类。一个课题可选多个方向。
- 课题与现有商机通过独立关联表建立多对多关系；关联不继承研究资料权限，也不复制附件。
- 概念快照、送审事实、技术经理决定及事件使用追加式表；旧记录禁止更新/删除。P1 仅建结构，不启用审批。
- 文件、成果、技术资产库、对客引用、产品工程和 Mixers 集成不在 P1 中。

## 表与关键字段

| 表 | 标识与主要字段 | 约束及审计 |
| --- | --- | --- |
| `development_topics` | `id`、独立 `topic_no`、`title`、`source_type`、`problem_statement`、`phase`、`result`、`owner_user_id`、`row_version`、时间戳 | 课题不依赖商机；创建人/负责人是真实用户外键；阶段与结果分列；新增课题自动写事件。P1 只创建 `idea`，不开放阶段推进。 |
| `development_topic_directions` | `topic_id`、`direction_code`、添加/结束操作者与时间 | 每课题每方向至多一条有效关系；仅允许 `process_technology`、`key_equipment`、`implementation_support`；结束不删除旧行，并自动写事件。 |
| `development_memberships` | `topic_id`、`user_id`、`responsibility_code`、加入/终止操作者与时间 | 每课题每用户至多一条有效成员关系；创建课题时负责人自动成为成员；终止不删除旧行。职责名称暂只使用 `owner`，不据此自行推定完整权限矩阵。 |
| `development_opportunity_links` | `topic_id`、`opportunity_id`、关联原因/操作者/时间、解除人/时间 | 两个真实外键；课题×商机至多一条有效关联，解除后历史行不删除，重新关联应另建一行；P1 不开放解除及商机界面。 |
| `development_concept_revisions` | `topic_id`、`revision_no`、结构化概念快照、SHA-256、作者/时间 | 同课题修订号唯一；快照必须是 JSON 对象；禁止更新/删除；具体一页式包验证在 P2。 |
| `development_concept_submissions` | `revision_id`、提交人/时间 | 每修订至多一次送审；禁止更新/删除；P2 才开放服务。 |
| `development_concept_decisions` | `submission_id`、决定、理由、决策人/时间、幂等键 | 仅已提交修订可有决定；每次送审至多一个决定；禁止更新/删除；数据库先拒绝非在职技术经理，P2 再由服务层与路由层检查对象、当前修订及待确认的自审规则。 |
| `development_events` | `topic_id`、`event_type`、操作者、关联修订、非敏感元数据、时间 | 自动记录本阶段新增及结束事实、课题版本更新；禁止更新/删除。事件不保存概念正文或研究附件内容。 |

`source_type` 候选值为客户创意、商机需求、既有产品升级、内部研发、实施反馈。`phase` 使用方案所列阶段码；`result` 可为空，不能由阶段推导。后续 P2 的暂停/恢复、核心方向重审和决定权限仍须经业务规则确认，P1 不提供这些操作。

## P1 仓储与验证

- 事务中创建课题、方向与负责人成员；任一失败则整体回滚。仓储只作为内部组件，不接入 `src/server.mjs`。
- 仓储可读单个课题、追加成员/商机关联和概念快照，但不提供绕开未来对象权限的 HTTP 能力。P2/P4 接入时必须再做服务层双边鉴权。
- 在隔离 PostgreSQL 数据库反复运行迁移，验证唯一键、外键、空字段、只读历史、事件自动记录和事务回滚；不得把验证脚本连向生产库。
- 待确认项仍按执行方案第 9 节保留：自审/代理、保密矩阵、文件政策、资产对客引用。P1 数据底座不把它们默认为已批准。

## 迁移、权限及回退说明

`083_development_foundation.sql` 仅新增序列、表、索引和新模块触发器，不修改现有商机、客户、工作项、附件或产品类别数据。应用目前没有装配新仓储，也没有菜单、页面或 `/development` 路由，因此 P1 不增加用户可操作权限。测试仅在临时的本地 PostgreSQL 容器执行；生产数据库未迁移。

若未来经单独审批上线，先备份并验证恢复，再执行迁移。发布后的应用回退可保留这些未接入的新增表；一旦产生研发记录，不应通过 `DROP TABLE` 回退，否则会丢失审计和研究历史。结构性撤销须另拟数据保全及恢复计划，并再次审批。
