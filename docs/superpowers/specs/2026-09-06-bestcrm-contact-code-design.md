# BESTCRM 联系人代码设计规范

- 日期：2026-09-06
- 状态：Frozen V1（用户已确认，分步实施中）
- 目标系统：新加坡 BESTCRM
- 当前客户代码：`C000001`
- 建议联系人代码：`CT000001`
- 下一数据库迁移：`044_contact_code.sql`

## 1. 目标

为每一条联系人主档分配一个稳定、永久、全局唯一的联系人代码，解决同名、同性、
同职务或联系方式变化时无法可靠区分联系人的问题。

联系人代码是业务可见标识，不替代数据库主键。数据库关系继续使用 `contacts.id`；
列表、详情、搜索和关联业务页面通过联表查询显示 `contact_code`，不在商机、邮件、
询价或工作记录中重复保存联系人代码。

## 2. 核心原则

1. 一个联系人主档只有一个代码。
2. 代码由数据库生成，用户不能填写或修改。
3. 联系人代码全系统唯一，不按客户分别编号。
4. 同名、同性、同职务联系人允许同时存在。
5. 姓名、性别、邮箱、电话、微信均不是唯一键。
6. 联系人改名、换职务、换电话、换邮箱或未来转移客户时，代码不变。
7. 已使用的代码不重新分配给其他联系人。
8. 业务关系只保存 `contact_id`，代码只从联系人主档读取。
9. 所有查询继续遵守现有客户负责人和角色可见性规则。
10. 联系人代码只用于 CRM 内部识别，不自动写入客户可见的邮件、报价或标书。

## 3. 编码规则

### 3.1 格式

```text
CT000001
CT000002
...
CT999999
```

- 固定前缀：`CT`
- 数字部分：6 位，不足左侧补零
- 正则约束：`^CT[0-9]{6}$`
- 字母固定大写
- 最大容量：999,999 个联系人

采用 `CT` 而不是 `C`，避免与客户代码 `C000001` 混淆。

### 3.2 生成规则

- PostgreSQL 序列：`contact_code_seq`
- 数据库默认值：`'CT' || lpad(nextval('contact_code_seq')::text, 6, '0')`
- 应用层创建联系人时不传入 `contact_code`
- 并发创建由数据库序列保证不重复
- 序列 `NO CYCLE`，耗尽时明确失败，不回收旧代码

### 3.3 不可变规则

数据库增加更新触发器。任何直接 SQL、后台脚本或应用代码试图修改已有
`contact_code` 时都必须失败。不能只依赖页面隐藏字段。

## 4. 数据库迁移

新增迁移 `src/db/migrations/044_contact_code.sql`，步骤如下：

1. 创建 `contact_code_seq`。
2. 给 `contacts` 增加可空字段 `contact_code text`。
3. 查询已有合法代码的最大数字部分；首次实施通常为 0。
4. 对缺少代码的历史联系人按 `contacts.id ASC` 稳定补码。
5. 将序列推进到已使用的最大编号。
6. 设置数据库默认值。
7. 设置 `NOT NULL`。
8. 创建唯一索引 `contacts_contact_code_unique_idx`。
9. 创建格式检查约束 `contacts_contact_code_format_check`。
10. 创建不可变函数和 `BEFORE UPDATE OF contact_code` 触发器。

历史补码只依赖内部 ID 顺序，不依赖姓名、性别、客户、邮箱或创建时间文本。
同一份生产备份排练和正式迁移会得到相同结果。

迁移是加法变更。旧版本程序会忽略新字段，因此应用回滚时不应删除字段、序列、
索引或历史代码。

## 5. 数据模型与读取规则

### 5.1 联系人主档

`contacts` 是联系人代码的唯一数据源：

```text
contacts
├── id                 数据库关系主键
├── contact_code       内部业务标识
├── customer_id        所属客户
├── name               姓名，可重复
├── title              职务，可重复
├── phone              可空、可变化、可重复
├── email              可空、可变化、可重复
├── wechat             可空、可变化、可重复
└── ...
```

### 5.2 下游关联

以下表继续只保存 `contact_id`：

- `opportunities.primary_contact_id`
- `inquiries.matched_contact_id`
- `email_threads.contact_id`
- `sales_work_plans.contact_id`
- `sales_work_logs.contact_id`
- 其他现有联系人外键

读取时通过 `contacts.id` 联表获取 `contact_code`。禁止向这些表新增
`contact_code` 副本，避免代码不一致。

询价中的原始 `contact_name`、`contact_email` 是客户来信快照，可以保留；一旦人工
确认联系人，则通过 `matched_contact_id` 连接联系人主档。快照不等于联系人身份。

## 6. 同名和可能重复联系人

### 6.1 允许的情况

以下情况均允许创建独立联系人：

- 同一客户中有两个同名联系人；
- 不同客户中有同名联系人；
- 同名、同性、同职务；
- 共用公司总机或公共邮箱；
- 联系方式暂时为空。

系统以 `contact_code` 明确区分，例如：

```text
CT000128 · Li Wei · Purchasing Manager · C000021 · ABC Ltd.
CT000376 · Li Wei · Purchasing Manager · C000084 · XYZ Pte. Ltd.
```

### 6.2 重复提示，不自动合并

联系人代码上线时不建立姓名、邮箱、电话或微信的唯一约束。后续重复检查采用
“提示而不阻止”的原则：

- 同一客户内规范化姓名相同；
- 规范化邮箱相同；
- 规范化电话相同；
- 规范化微信号相同。

候选提示必须显示联系人代码、姓名、所属客户代码及客户名称。用户可以打开候选
联系人核对，也可以确认创建新联系人。系统不得自动合并，不得仅凭同名或性别判断
为同一个人。

重复候选查询必须应用与联系人列表相同的权限范围，不能向销售人员泄露其无权查看
的客户或联系人。

## 7. 页面和搜索

### 7.1 联系人列表 `/contacts`

- 第一列新增“联系人代码”；
- 代码链接到联系人详情；
- 增加服务端搜索框；
- 支持联系人代码、姓名、所属客户代码、客户名称、邮箱、电话和微信搜索；
- 搜索结果仍受当前客户负责人权限限制；
- 保留当前创建时间倒序，不因代码上线改变默认排序。

建议显示：

```text
联系人代码 | 姓名 | 客户 | 职务 | 电话 | 邮箱
CT000128   | Li Wei | C000021 · ABC Ltd. | Purchasing Manager | ... | ...
```

### 7.2 联系人详情 `/contacts/:id`

- 标题下显示 `CT000128 · Li Wei`；
- 基本资料第一行显示“联系人代码”；
- 代码为只读文本，不进入编辑表单；
- 所属客户显示 `C000021 · ABC Ltd.`。

### 7.3 新建和编辑联系人

- 新建页提示“联系人代码将在保存后自动生成”；
- 编辑页显示只读代码；
- POST 请求忽略任何客户端提交的 `contactCode`；
- Repository 的 INSERT/UPDATE 不接受代码参数。

### 7.4 客户详情

客户详情的联系人表第一列显示联系人代码。联系人名称重复时，用户仍可通过代码、
职务、电话和邮箱区分。

### 7.5 商机

- 商机列表的主要联系人显示 `CT000128 · Li Wei`；
- 联系人筛选选项显示联系人代码、姓名及客户代码/名称；
- 商机新建/编辑的联系人选项显示同样的完整标签；
- 商机详情的主要联系人链接显示联系人代码和姓名；
- 商机搜索增加联系人代码匹配；
- 不改变现有 `visibleToUserId`、负责人、成员和审批角色可见性规则。

### 7.6 询价

- 人工匹配联系人下拉框显示联系人代码、姓名及客户；
- 已匹配联系人摘要显示联系人代码；
- 原始来信中的联系人姓名/邮箱继续作为快照展示；
- 没有 `matched_contact_id` 时不伪造联系人代码。

### 7.7 工作记录

- 工作计划和工作记录中的联系人显示联系人代码与姓名；
- 联系人下拉选项显示代码、姓名和客户；
- 仍然只保存 `contact_id`。

### 7.8 邮件中心

邮件中心当前生产开关保持关闭，本设计不启用邮件功能。代码实现应为以后开启做好
读取能力：

- 邮件会话列表和详情显示 `CT000128 · Li Wei`；
- `email_threads` 继续只保存 `contact_id`；
- 同一邮箱命中多个联系人时，代码用于人工区分；
- 没有可靠回复链或人工确认时，不因联系人代码功能自动归入商机。

### 7.9 客户可见文件

联系人代码默认不写入以下外部内容：

- 发给客户的邮件正文和签名；
- 报价 PDF、技术方案、商务包和标书；
- 客户下载的附件文件名。

如未来确有外部引用需求，应单独设计模板字段和审批规则。

## 8. Repository 和服务变更

### 8.1 `contactRepository`

- `mapContactRow` 增加 `contactCode`；
- 所有联系人 SELECT 返回 `ct.contact_code`；
- `listContacts` 增加 `searchTerm`，使用参数化 `ILIKE` 并转义 `%`、`_`、`\\`；
- 保留 `ownerUserId` 和 `customerId` 过滤条件；
- INSERT/UPDATE 不允许写联系人代码。

### 8.2 其他读取模型

按实际展示范围增加联表字段：

- `customerRepository` 的客户详情联系人列表；
- `opportunityRepository` 的主要联系人和筛选选项；
- `inquiryRepository` 的已匹配联系人；
- `emailArchiveRepository` 的邮件会话联系人；
- `salesWorkRepository` 的工作计划和日志联系人；
- 内部标书工作区中已显示联系人的读取模型。

所有 JavaScript 映射统一使用 `contactCode`，数据库字段统一使用 `contact_code`。

### 8.3 路由

`GET /contacts` 接收 `search` 查询参数，只将规范化搜索词传给 Repository。路由不能
在内存中加载全部联系人后过滤，也不能绕过 Repository 的负责人过滤。

## 9. 多语言

增加以下中英文文案：

- `contactCode`: Contact code / 联系人代码
- `contactSearchPlaceholder`: Search by contact code, name, customer, email, phone, or WeChat / 按联系人代码、姓名、客户、邮箱、电话或微信查询
- `contactCodeGeneratedAfterSave`: Contact code will be generated after saving / 保存后自动生成联系人代码
- `possibleDuplicateContacts`: Possible duplicate contacts / 可能重复的联系人

## 10. 权限与安全

- 代码本身不是访问令牌，不改变授权模型；
- 知道联系人代码不能绕过联系人详情权限；
- 搜索联系人代码必须应用当前角色和客户负责人过滤；
- 邮件、询价、商机和工作记录继续使用各自现有可见性服务；
- 管理员可以查看全部联系人；普通销售只查看其可维护客户的联系人；
- 任何直接 URL 访问仍进行服务端权限检查。

## 11. 删除和归档边界

本次联系人代码实施不扩大删除权限。当前联系人删除仍仅限管理员，并继续受数据库
外键限制。即使联系人被允许删除，序列也不会重用其代码。

由于部分历史关系采用 `ON DELETE SET NULL`，长期正确方案应将“删除联系人”单独重构
为“归档联系人”：保留代码和历史关联，阻止其出现在新业务选择框，但允许在旧商机、
邮件和工作记录中查看。这属于后续独立设计，不与联系人代码迁移混在同一发布中。

## 14. 验收标准

设计实施完成后必须同时满足：

1. 每个联系人均有且只有一个 `CT000001` 格式代码。
2. 两个同名联系人可以创建并通过代码清楚区分。
3. 用户不能输入或修改代码。
4. 联系人代码可在联系人列表中搜索。
5. 客户、商机、询价、工作记录和邮件读取界面显示同一主档代码。
6. 下游业务表没有联系人代码副本。
7. 权限范围与实施前一致。
8. 历史联系人补码无空值、无重复、无非法格式。
9. 客户代码和现有商机流程无回归。
10. 邮件生产功能保持关闭，除非另行批准。
