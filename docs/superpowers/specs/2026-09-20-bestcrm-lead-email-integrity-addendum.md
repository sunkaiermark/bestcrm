# BESTCRM 线索入口与邮件完整性补充规范

状态：用户于 2026-09-20 确认并冻结。

本规范补充 `docs/email-center-final-design.md` 和
`docs/superpowers/specs/2026-09-12-bestcrm-email-triage-framework.md`。发生冲突时，
本规范优先。未经新的日期化补充规范和用户明确确认，不得改变以下规则。

## 1. 单一商机入口

1. 所有在职 CRM 用户都可以提交线索。
2. `sales@sunkaier.com` 新收件、官网表单和员工手工录入都必须先形成线索，
   不能直接创建新商机。
3. 已明确关联现有商机的邮件直接进入该商机，不重复建立线索。
4. 无法关联现有商机的邮件进入“待处理”。获授权处理人只能把它转为线索、
   关联已有商机、标记垃圾邮件或标记非业务邮件。
5. 新线索提交销售经理审核。销售经理确认其为真实业务机会、销售负责人、客户和
   联系人后，系统才在同一数据库事务中生成商机及商机号码。
6. 未转换线索可以删除。删除邮件来源线索不得删除邮件；必须把邮件退回“待处理”，
   或在同一操作中明确转入“垃圾邮件”或“非业务邮件”。
7. 线索一旦转换为商机，来源线索、商机及其邮件关联均成为不可删除的业务历史，
   只允许按既定权限归档或更正，并保留审计记录。
8. 所有允许来源的来信先进入临时待处理区，以防漏掉客户询盘；待处理是工作缓冲区，
   不是永久邮件档案。
9. 只有确认属于客户业务、线索、商机或其后续交流的邮件，才晋升为长期业务邮件。
10. 人工确认并执行永久清理的垃圾邮件和可删除非业务邮件必须删除 CRM 中的原始 `.eml`、
    邮件头、正文、地址、文件名、内嵌资源和附件，不得因为“审计完整”而永久保留垃圾内容。
11. 清理后只保留防重导所需的最小不可逆身份摘要和删除事件：处理人、时间、原因、数量、
    字节数及邮箱投递身份摘要。该记录不是邮件，不得用于还原发件人、主题、正文或附件。

## 2. 权威邮件数据模型

1. PostgreSQL 是全部业务状态的唯一事实来源。客户、联系人、线索、商机、权限、流程
   状态、审批、邮件关系、投递状态、任务游标和审计结果不得只存在于页面、浏览器
   `localStorage`、Node.js 进程内存、临时文件名或定时任务日志中。
2. 更换或重写应用程序时，只要新程序遵守已冻结的数据合同和迁移规则，就必须能够从
   数据库恢复全部业务对象、关系、状态和历史；程序崩溃不得造成业务状态回退或重复执行。
3. 数据库必须记录当前结构迁移版本、兼容的应用发布身份以及每个外部文件的稳定身份、
   路径、大小、SHA-256、状态和归属，恢复程序不得依赖聊天记录或人工记忆解释数据。
4. 邮件原文和附件的实际字节存放在不可变文件库，不应仅为了“单一数据库文件”而把大量
   MIME 和附件盲目塞入 PostgreSQL。数据库与其登记的不可变文件库共同组成完整数据集；
   数据库可以证明文件应当存在及内容哈希，但不能从哈希重新生成已经丢失的文件字节。
5. 完整灾难恢复单元固定为：兼容的 Git 发布版本、数据库备份及迁移记录、不可变原始
   EML/附件文件库、文件清单与哈希、受保护环境配置。任何一项缺失都不能宣称可完整重建。

### 2.1 邮件实体约束

1. 一封仍在待处理或已确认保留的 RFC 邮件，在 CRM 中只能有一个权威 `email_message`
   记录和一份不可变原始
   MIME `.eml`。收件箱、已发件箱、商机往来和线索详情只是同一记录的不同查询视图，
   不能复制出互相独立的正文或附件。
2. 同一邮件到达多个受控文件夹时，只增加不可变的邮箱投递观察记录，不重复创建业务
   邮件。标准化 `Message-ID` 为主身份，邮箱、文件夹、UIDVALIDITY、UID 和内容指纹
   共同承担幂等和冲突核对。
3. `email_thread` 保存会话关系；`email_message` 保存方向和内容；邮箱投递、附件、
   原始 MIME、扫描结果、分类事件、处理事件和发送尝试分别保存，不得混入可覆盖字段。
4. 线索、客户、联系人和商机只引用权威邮件会话，不拥有第二份邮件副本。
5. 所有外键必须防止产生孤立邮件、孤立附件或失去来源的商机。业务关联邮件禁止级联
   删除；不可变邮件、附件、投递及审计记录由数据库约束或触发器保护。
6. 永久清理只允许作用于没有当前或历史业务关系、没有出站邮件、没有回复链依赖且已由
   管理员确认的垃圾邮件或非业务邮件。清理事务必须先证明其不属于业务档案。

## 3. 收件箱与已发件箱

1. “待处理”只显示尚未完成业务归类的入站会话。
2. 邮件转为线索后立即离开“待处理”，进入“收件箱”并显示“线索审核中”，避免多人
   重复处理；此时尚不生成商机号码。
3. 销售经理批准线索时，系统把同一邮件会话自动关联新商机、客户和联系人，同时保留
   来源线索链路，不移动、不复制邮件。
4. “收件箱”显示已关联线索或商机的入站邮件；“已发件箱”只显示已关联商机的出站
   邮件。草稿不得伪装成已发送邮件。
5. 已关联商机的客户回复自动进入原会话、商机时间轴和收件箱，并通知商机销售负责人。
   无法可靠匹配的来信必须回到“待处理”，不得猜测关联。
6. CRM 只读取网易 `sales@sunkaier.com` 的真实收件箱和已发送文件夹，不改变网易的
   已读状态，不从 CRM 移动或删除网易原邮件。

## 4. 标准邮件头与会话关系

1. 必须解析并保留 `From`、`Sender`、`Reply-To`、`To`、`Cc`、`Date`、`Subject`、
   `Message-ID`、`In-Reply-To`、`References`、MIME 版本和内容类型。CRM 自己发送的
   `Bcc` 仅按权限保存在内部，不得泄露给其他收件人或无权用户。
2. 回复必须使用标准 `In-Reply-To` 和完整 `References` 链，优先据此归入原会话。
3. CRM 对外回复时，服务器在主题中强制保留且只保留一个正确的
   `[REF. 商机号码]`。REF 是辅助匹配与网易检索字段，不能替代标准回复头。
4. 原始邮件头日期、提供方实际接收时间、CRM 导入时间和 CRM 发送完成时间分别保存。
   数据库存储带时区时间；时间轴使用可信的收发时间排序，并可展开查看原始邮件日期。
5. 重复导入必须幂等。相同邮件不能产生第二封邮件、第二条待处理任务或第二个线索；
   身份冲突必须进入人工核对和审计，不能静默覆盖。

## 5. 正文、签名和脚注

1. 原始 MIME、原始纯文本和原始 HTML 均保持不变。阅读版面可以生成派生的安全 HTML
   或视觉重排文本，但不得回写覆盖原文。
2. 正文必须正确处理字符集、换行、段落、列表、表格、历史引用和国际文字方向。
3. HTML 阅读采用隔离和净化渲染；脚本、表单、自动跳转和危险 URL 禁止执行，外部
   图片默认不加载。安全处理不能删除原始 MIME 中的证据。
4. CID 内嵌图片、公司 Logo 和邮件内表格应在权限检查后从本地归档显示。
5. CRM 发件采用 `multipart/alternative` 等标准 MIME 结构，同时生成相符的纯文本和
   HTML 正文。用户编辑正文、动态姓名和职务、公司签名、地址及保密声明共同组成最终
   内容；预览必须与最终发送内容一致。
6. 引用历史默认折叠但可完整展开；不得把客户原文误当作新回复正文，也不得在每次
   回复中无限重复叠加 CRM 签名。

## 6. 附件完整性

1. 每个附件和内嵌资源按原字节保存，并记录原文件名、标准化显示名、MIME 类型、大小、
   SHA-256、Content-ID、Content-Disposition、所属邮件和源序号。
2. 同名附件不能互相覆盖。附件必须通过受登录、角色和业务关联权限控制的接口读取，
   存储目录不得公开暴露。
3. 邮件转线索或商机时，原附件仍属于原邮件。需要成为“客户需求文件”时建立受审计的
   引用或派生副本，不能改变或替换原附件。
4. 附件保存、恶意内容扫描或哈希核对失败时，邮件不得被标记为“完整归档”；系统必须
   保留可重试状态和安全错误记录。

## 7. 来信回信时间轴与阅读回复

1. 商机“往来沟通”按会话显示标准来信回信时间轴，入站与出站方向清楚，默认展开最新
   邮件，其余邮件可展开，不另建第二套邮件数据。
2. 每封邮件摘要必须显示真实发件人、收件人、抄送、主题、收发时间、方向和投递状态；
   完整邮件头可以展开查看。
3. 正文使用可用横向宽度，附件固定列在所属邮件正文下方；手机端不得因宽表格、长链接、
   长文件名或引用缩进撑破页面。
4. “回复客户”是商机唯一对外回复入口。回复默认针对最新客户来信，并使用该邮件的
   标准回复头；多个独立会话时必须先选会话。
5. 草稿、待批准、发送中、已发送和发送失败必须是清楚、互斥的状态。只有 SMTP 明确
   成功且最终归档校验完成后，才能显示“已发送”。失败重试沿用同一逻辑邮件身份并记录
   每次投递尝试，不能制造重复发件。

## 8. 原子性、审计和故障恢复

1. 转线索、关联商机、线索批准转商机和邮件最终分类都必须使用数据库事务和并发锁。
   同一待处理邮件只能有一名处理人成功；同一线索只能转换一次；商机号码只能在成功
   转换时分配。
2. 文件先写入隔离暂存区并完成大小、哈希和扫描校验，再用数据库事务建立最终索引；
   提交失败时执行可审计补偿，不能留下“数据库显示完整但文件缺失”的邮件。
3. 最终 MIME 只构造一次。SMTP 发送、CRM 归档和网易已发送对账必须基于同一最终内容
   身份；提供方新增的传输头单独作为投递证据保存，不得回写改变 CRM 原稿。
4. 所有分类、关联、解除未转换线索关联、批准、退回、发送、失败、重试、归档和删除
   操作记录操作者、时间、前后状态、目标记录和安全原因。审计记录不可修改。
5. 任何结构迁移或清理前必须创建并验证数据库、上传文件、原始 EML 和环境配置备份；
   数据校验失败时停止发布或回退，不能带病继续。
6. 每个备份必须生成可离线读取的恢复清单，至少记录 Git 提交/标签、迁移版本、数据库
   摘要、文件数、总字节数、文件清单摘要、环境配置摘要和创建时间；摘要不得包含密钥值。
7. 备份存在不等于可以恢复。重大迁移和定期运维必须在隔离环境执行实际恢复演练，并以
   数据库约束检查、文件哈希核对、邮件重建抽查和关键业务流程读取成功作为恢复完成标准。
8. 已被永久清理的垃圾邮件可能仍存在于尚未到期的历史只读备份中；不得为抹除单封邮件
   而破坏已验证备份。备份按既定保留周期整体到期销毁；从旧备份恢复时，必须在 CRM 对外
   开放前重放其后的最小清理标记，避免已清理垃圾邮件重新进入活动数据库。
9. 永久清理必须采用数据库持久化的清理任务。删除邮件图的同一事务必须写入防重标记和
   待删除文件路径；事务提交后由可重复执行的回收器删除文件。文件不存在视为幂等成功，
   失败状态和路径保留到重试成功；完成后清除可识别路径，只留下最小清理审计。不得先删
   数据库记录、再仅靠当前 HTTP 请求临时变量删除文件。

## 9. 实施验收门槛

以下项目全部通过后，相关功能才可进入新加坡发布候选：

1. 重复导入、并发处理和并发转换测试证明不会重复建邮件、线索、商机或商机号码。
2. 随机抽取收件、发件、HTML、纯文本、CID、国际字符和多附件邮件，证明页面内容可由
   保存的 `.eml` 重建，附件字节和 SHA-256 一致。
3. 完整验证 `Message-ID -> In-Reply-To/References -> REF -> 商机` 的匹配顺序及无法匹配
   时回到待处理的安全行为。
4. 验证删除未转换线索不会删除邮件；已转换线索、商机、业务邮件和审计历史均被数据库
   拒绝物理删除。
5. 模拟文件写入失败、数据库提交失败、SMTP 超时和服务重启，确认不存在错误“已发送”、
   半封邮件、孤立附件或丢失回复。
6. 桌面端和手机端截图确认收件箱、已发件箱、完整邮件头、正文、签名、保密脚注、附件、
   时间轴及唯一回复入口。
7. 本地重点测试、完整测试和数据库完整性检查全部通过，再建立 Git 检查点；获得用户确认
   后才允许备份并部署新加坡。
8. 使用指定 Git 发布、数据库备份、文件归档和受保护配置在隔离目录完成一次从零重建；
   重建后客户、线索、商机、邮件时间轴、原始 EML、附件和审计数量及哈希必须与恢复清单
   一致。只有通过该演练，才能声明系统具备“程序崩溃后按数据重建”的能力。
9. 恢复演练必须证明永久清理过的垃圾邮件不会因恢复或重新扫描网易文件夹而重新出现；
   活动数据库中只保留已清理后的业务邮件及其业务关系和最小清理标记。
10. 模拟数据库清理提交后、磁盘文件删除前进程崩溃，确认服务重启后能够从持久化清理任务
    继续回收文件，并在完成后不留下垃圾正文、附件、原始 EML、孤立文件或明文文件路径。
